## 1. 首期交付：知识库底座（R1）

ARIA 在贵司内网建立的不仅是「报价工具」，而是 **按完整历史项目打包管理的企业资料库**：

| 能力 | 第一期含 | 说明（业务语言） |
|------|---------|-----------------|
| 历史项目包关联 | ✓ | 同一项目的 RFQ、Q&A、报价 **绑在一起**，不是散乱文件 |
| 分类型读取与建目录 | ✓ | RFQ 按章节、Q&A 按行、报价读成人天数字，供检索与核对 |
| 按意思找相似资料 | ✓ | Top-3 对标；知识库页 **检索试用** |
| 人天对照预览 | ✓ | 报价 Excel 人天与源表 **人工核对**（不是 AI 填数） |
| IT 文件夹批量入库 | ✓ | 内网服务器放文件夹 + 网页 **更新检索目录**（**大批量推荐**） |
| 网页小批量上传 | ✓ | 知识库页 **一次 1～5 套**；缺件有提示 |
| **两阶段入库配合** | ✓ | **前期**：脱敏金标准 + 结构试点联调；**后期**：贵司内网 **真实历史库** bulk 落盘与验收 |
| **清点表锁定范围** | ✓ | 签约后 2 周内双方填写计划入库套数、齐全率、常见缺件（**合同不写死总数**） |
| 网页拖拽整目录、断点续传 | ✗ | 后续可选增强 · **变更单** |
| 分角色权限 | ✗ | 后续阶段 |
| **网页点「结果不准」反馈** | ✗ | 第一期用 **检索试搜记录表**；后续可选 |
| **反馈运营看板** | ✗ | 后续可选 · 变更单 |

**资料存放位置：** 贵司内网服务器数据盘上的 **历史项目文件夹**（与数据库、备份在一起，可整体备份迁移）。

**与 R1 验收的关系：** ≥5 套 **金标准**三件套逐套验收；内网 bulk 规模以 **清点表** 为准；缺 Q&A 或缺报价的项目 **仍可入库**（银级/铜级），导入报告标明对第二、三期的影响。

## 2. 首期 vs 持续优化（客户必读）

很多客户会问：**「资料越加越多，AI 会不会越用越准？」** 请区分下面两层：

| 层次 | 第一期（¥18.3 万）已含 | 第一期不含（需另议） |
|------|------------------------|---------------------|
| **能用的底座** | **≥5 套金标准** + **内网历史项目库**（套数以清点表为准）；Top-3 对标（**第一期签完即用**）；≥15 条检索试搜（≥12/15 通过） | — |
| **资料越多** | **可引用历史越多**（覆盖更全）；须规范三件套 + **更新索引** 后生效 | **不会** 因加文档就自动变准 |
| **发现引用不对** | R1 **检索评测记录表**（验收期人工标注）；日常 **改对比表 / 确认维度** | 网页 **「引用不准」按钮**（L1）；**自动学习**（L2） |
| **谁「知道错了」** | **工程师 + 验收签字**；不是大模型自己记住 | 系统 **存反馈记录** → 管理员/乙方 **定期审查** → 改 metadata / 补评测题 / 重跑索引 |

**一句话：** 第一期保证 **可检索、可验收、工程师可定稿**；「越用越准」的 **产品化飞轮** 在 M6 后运营包（见 §4），**不是** 本地大模型点一下按钮就 overnight 变聪明。

**加文档会不会更快？** 不会明显加快生成速度；库变大后检索略增耗时。主要收益是 **找得更全**，不是 **跑得更快**。

## 3. 平台三层路线图（与首期合同的关系）

```
ARIA 平台（历史资料库 + 本地 AI）
    └── 报价助手（首期应用：RFQ → Q&A → 报价 → 技术方案）  ← ¥18.3 万合同
    └── 知识库运营增强（M6 后可选）                        ← 本文 §4
    └── 财务助手、系统集成等（远期规划）                    ← [平台扩展愿景](./ARIA%20平台扩展愿景（客户版）.md)
```

| 阶段 | 大约时间感 | 客户主要得到什么 | 是否在 ¥18.3 万内 |
|------|-----------|-----------------|------------------|
| **首期合同（R1→M6）** | 签约后约 20 周 | 知识库底座 + 报价助手五步（**分期解锁**；R1 第 8 周起可日常 RFQ 对标） | **是** |
| **知识库运营增强** | M6 稳定运行后 | 大批量上传、反馈 L1/L2、定稿归档、检索升级、运营看板等（§4） | **否 · 变更单/运维包** |
| **平台新应用与集成** | 远期规划 | 财务助手、OA/PLM 对接、多语言 RFQ 等 | **否 · 另立项** |

**长期价值：** 历史项目资料 **入库一次、多个环节共用**；以后新增应用 **不必重复建库、不必重复采购 GPU 基础设施**。报价助手各期（人力 Excel、Q&A、PPT）的交付节奏见 [客户易懂版 §五](./ARIA-报价助手-正式版交付方案与报价（客户易懂版）.md)；**本文专注知识库如何长大与如何运营**。

## 4. 第二期增强：您会得到什么（业务语言）

> **说明：** 下列能力 **不在首期 ¥18.3 万合同内**；上线稳定后，可按需 **变更单 / 续费 / 年度运维包** 选购。  
> **不影响** 第一期 R1 验收与付款。

### 4.1 总览：第一期 vs 第二期

| | **第一期（已规划交付）** | **第二期增强（可选）** |
|---|------------------------|------------------------|
| **核心目标** | 能检索、能对标、能出草稿、能验收签字 | 更好 **运营**、更好 **补资料**、检索 **越用越顺** |
| **历史资料怎么进库** | IT 放目录 + 管理员点「更新索引」；或网页一次传 ≤5 套 | 大批量 **拖拽上传**、断点续传、定稿 **一键归档进库** |
| **发现检索不对怎么办** | 验收评测表 + 工程师改对比表 | 网页 **点一下留记录** → 管理员 **定期复盘改进** |
| **检索能力** | 按意思找 Top-3 + 条件筛选 | 项目代号 **更准** + 相似项目 **更智能** 组合查找 |
| **谁主要用** | 报价工程师 + IT | + **知识库管理员** 日常运营 |

---

### 4.2 分项说明（按您关心的问题）

#### ① 大批量上传门户（运营级）

| | |
|---|---|
| **您感受到** | 不用每次只传 5 套；IT/管理员可 **拖整个文件夹** 上传，传一半断了 **能续传** |
| **解决什么** | 贵司现有历史项目库 **补库更省力**，少找乙方做批量脚本 |
| **谁用** | IT、知识库管理员 |
| **第一期已有** | 目录批量 + 小网页上传（≤5 套/次） |

#### ② 引用反馈 · 收集（L1）

| | |
|---|---|
| **您感受到** | 检索结果或相似项目 **不对**，在网页点 **「不相关 / 不应出现」**，系统 **记下来** |
| **解决什么** | 不用每次发邮件报问题；有问题 **留痕** |
| **不会发生什么** | **不会** 点完大模型立刻变聪明（不训练 AI） |
| **建议时机** | M6 上线后 1 个月内（可选小包） |

#### ③ 引用反馈 · 运营闭环（L2）

| | |
|---|---|
| **您感受到** | 管理员 **看哪些检索常出错**；**每季度** 和乙方一起改评测题、补资料、重建索引 → **同类问题越来越少** |
| **解决什么** | 把「越用越准」变成 **可重复流程**，不是口头说说 |
| **谁用** | 管理员 + 业务负责人 + 乙方运维 |
| **与 L1 关系** | L1 = 收集；L2 = **审查 + 改进 + 看板** |

#### ④ 定稿项目一键进历史库

| | |
|---|---|
| **您感受到** | 某次报价 **定稿后**，点一下把本次 RFQ、Q&A、人力 Excel **归档为新的历史项目**，下次对标 **能搜到** |
| **解决什么** | 知识库 **随业务自然长大**，不用每次手工拷文件夹 |
| **第一期** | **不含**；定稿资料仍在任务目录，须 **手动** 按规范入库 |
| **建议时机** | M6 后 hypercare 或运营包 |

#### ⑤ 检索运营看板

| | |
|---|---|
| **您感受到** | 管理员看到：**哪些领域历史资料还缺**、**大家常搜什么词**、**哪些项目从未被引用** |
| **解决什么** | 知道下一步该 **补哪类项目包**，而不是盲目加文件 |
| **谁用** | IT、知识库管理员、业务负责人 |

#### ⑥ 资料过期提醒

| | |
|---|---|
| **您感受到** | 太老的 RFQ/报价 **标红或提醒**，避免误用过期模板或旧商务条件 |
| **解决什么** | 合规与 **资料新鲜度** |
| **谁用** | 管理员制定规则；工程师上传/检索时看到提示 |

#### ⑦ 检索升级包（项目代号更准 + 相似更智能）

| | |
|---|---|
| **您感受到** | 输入 **项目代号、客户简称** 时 **更容易精确命中**；同时仍可按 **技术描述** 找相似项目 |
| **解决什么** | 第一期主要是 **按意思相似**；工程师常抱怨「名字要对上」时考虑此包 |
| **第一期** | Top-3 智能相似 + 筛选；**不含** 全文组合增强 |
| **建议形态** | 独立 **技术升级变更单** |

#### ⑧ 增量更新（只处理新文件）

| | |
|---|---|
| **您感受到** | 库内历史项目较多时，**只索引新增/改动的文件**，不用每次 **整库重跑** 等很久 |
| **解决什么** | 日常补几套资料 **更快** |
| **第一期** | 触发索引时偏 **全量**；新文件须管理员 **主动点** 更新 |

#### ⑨ 分角色权限（可选）

| | |
|---|---|
| **您感受到** | 工程师 **只能检索和使用**；管理员 **才能上传、删改、重建索引** |
| **解决什么** | 多人用时 **防误操作** |
| **第一期** | 内网管理员共用；细粒度权限 **不含** |

## 5. 对 IT 的说明

- **R1：** IT 目录批量 **或** 知识库页 **单套/小批量 Web 上传（≤5 套/次）**；开发方提供模板与验收
- **运维：** 备份 / 启停 / 重建索引脚本随 M6 移交
- **扩展：** 新 doc_type 或新应用通过 manifest + ingest 扩展，**不破坏**现有 Engagement 结构
