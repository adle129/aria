## 1. 首期交付：知识库底座（R1）

ARIA 在贵司内网建立的不仅是「报价工具」，而是 **Engagement 企业知识库**：

| 能力 | R1 含 | 说明 |
|------|-------|------|
| Engagement 项目包 | ✓ | RFQ + Q_A + 报价 manifest 关联 |
| 分类型切块与索引 | ✓ | RFQ 章节、Q_A 按行、报价结构化 baselines |
| 向量检索 | ✓ | Top-3 RFQ 对标；检索实验室 |
| 基线预览 | ✓ | 人天 baselines 与源 Excel 对照 |
| IT 文件夹入库 | ✓ | 规范目录 + 批量导入（**100+ 推荐**） |
| Web 单套/小批量上传 | ✓ | 知识库页 **≤5 套/次**；缺件提示 |
| Web 运营级上传门户 | ✗ | 拖拽整目录、断点续传等 · **变更单** |
| 细粒度权限 | ✗ | Phase 2+ |
| **引用反馈（网页点选）** | ✗ | **M6 后可选 L1**；R1 用评测表（见 §2） |
| **反馈运营闭环（看板+自动变准）** | ✗ | Phase 2 **L2** · 变更单 |

**数据位置：** `${ARIA_DATA_ROOT}/app/knowledge_base/` — 与业务库、向量库同盘，可备份迁移。

## 2. 首期 vs 持续优化（客户必读）

很多客户会问：**「资料越加越多，AI 会不会越用越准？」** 请区分下面两层：

| 层次 | 第一期（¥18.3 万）已含 | 第一期不含（需另议） |
|------|------------------------|---------------------|
| **能用的底座** | 3–5 套金标准验收；Top-3 对标；≥15 条检索评测（≥12/15 通过）；工程师审阅定稿 | — |
| **资料越多** | **可引用历史越多**（覆盖更全）；须规范三件套 + **更新索引** 后生效 | **不会** 因加文档就自动变准 |
| **发现引用不对** | R1 **检索评测记录表**（验收期人工标注）；日常 **改对比表 / 确认维度** | 网页 **「引用不准」按钮**（L1）；**自动学习**（L2） |
| **谁「知道错了」** | **工程师 + 验收签字**；不是大模型自己记住 | 系统 **存反馈记录** → 管理员/乙方 **定期审查** → 改 metadata / 补评测题 / 重跑索引 |

**一句话：** 第一期保证 **可检索、可验收、工程师可定稿**；「越用越准」的 **产品化飞轮** 在 Phase 2 运营包（见 §3），**不是** 本地大模型点一下按钮就 overnight 变聪明。

**加文档会不会更快？** 不会明显加快生成速度；库变大后检索略增耗时。主要收益是 **找得更全**，不是 **跑得更快**。

## 3. 平台 vs 首期应用

```
ARIA 平台（知识库 + 本地 LLM + RAG）
    └── 报价助手（首期应用：RFQ → Q_A → 报价 → Proposal）
    └── 财务助手等（规划，复用同一 KB）
```

**长期资产：** 历史项目资料 **一次入库、多应用消费**；新应用挂载时 **不重搭** GPU、PostgreSQL（含 pgvector）、Ollama。

## 4. 第二期增强：您会得到什么（业务语言）

> **说明：** 下列能力 **不在首期 ¥18.3 万合同内**；上线稳定后，可按需 **变更单 / 续费 / 年度运维包** 选购。  
> **不影响** 第一期 R1 验收与付款。

### 4.1 总览：第一期 vs 第二期

| | **第一期（已规划交付）** | **第二期增强（可选）** |
|---|------------------------|------------------------|
| **核心目标** | 能检索、能对标、能出草稿、能验收签字 | 更好 **运营**、更好 **补资料**、检索 **越用越顺** |
| **历史资料怎么进库** | IT 放目录 + 管理员点「更新索引」；或网页一次传 ≤5 套 | 大批量 **拖拽上传**、断点续传、定稿 **一键归档进库** |
| **发现检索不对怎么办** | 验收评测表 + 工程师改对比表 | 网页 **点一下留记录** → 管理员 **定期复盘改进** |
| **检索能力** | 按意思找 Top-3 + 条件筛选 | 项目代号 **更准** + 相似项目 **更智能** 组合查找 |
| **谁主要用** | 报价工程师 + IT | + **知识库管理员** 日常运营 |

---

### 4.2 分项说明（按您关心的问题）

#### ① 大批量上传门户（运营级）

| | |
|---|---|
| **您感受到** | 不用每次只传 5 套；IT/管理员可 **拖整个文件夹** 上传，传一半断了 **能续传** |
| **解决什么** | 100+ 历史项目 **补库更省力**，少找乙方做批量脚本 |
| **谁用** | IT、知识库管理员 |
| **第一期已有** | 目录批量 + 小网页上传（≤5 套/次） |

#### ② 引用反馈 · 收集（L1）

| | |
|---|---|
| **您感受到** | 检索结果或相似项目 **不对**，在网页点 **「不相关 / 不应出现」**，系统 **记下来** |
| **解决什么** | 不用每次发邮件报问题；有问题 **留痕** |
| **不会发生什么** | **不会** 点完大模型立刻变聪明（不训练 AI） |
| **建议时机** | M6 上线后 1 个月内（可选小包） |

#### ③ 引用反馈 · 运营闭环（L2）

| | |
|---|---|
| **您感受到** | 管理员 **看哪些检索常出错**；**每季度** 和乙方一起改评测题、补资料、重建索引 → **同类问题越来越少** |
| **解决什么** | 把「越用越准」变成 **可重复流程**，不是口头说说 |
| **谁用** | 管理员 + 业务负责人 + 乙方运维 |
| **与 L1 关系** | L1 = 收集；L2 = **审查 + 改进 + 看板** |

#### ④ 定稿项目一键进历史库

| | |
|---|---|
| **您感受到** | 某次报价 **定稿后**，点一下把本次 RFQ、Q&A、人力 Excel **归档为新的历史项目**，下次对标 **能搜到** |
| **解决什么** | 知识库 **随业务自然长大**，不用每次手工拷文件夹 |
| **第一期** | **不含**；定稿资料仍在任务目录，须 **手动** 按规范入库 |
| **建议时机** | M6 后 hypercare 或运营包 |

#### ⑤ 检索运营看板

| | |
|---|---|
| **您感受到** | 管理员看到：**哪些领域历史资料还缺**、**大家常搜什么词**、**哪些项目从未被引用** |
| **解决什么** | 知道下一步该 **补哪类项目包**，而不是盲目加文件 |
| **谁用** | IT、知识库管理员、业务负责人 |

#### ⑥ 资料过期提醒

| | |
|---|---|
| **您感受到** | 太老的 RFQ/报价 **标红或提醒**，避免误用过期模板或旧商务条件 |
| **解决什么** | 合规与 **资料新鲜度** |
| **谁用** | 管理员制定规则；工程师上传/检索时看到提示 |

#### ⑦ 检索升级包（项目代号更准 + 相似更智能）

| | |
|---|---|
| **您感受到** | 输入 **项目代号、客户简称** 时 **更容易精确命中**；同时仍可按 **技术描述** 找相似项目 |
| **解决什么** | 第一期主要是 **按意思相似**；工程师常抱怨「名字要对上」时考虑此包 |
| **第一期** | Top-3 智能相似 + 筛选；**不含** 全文组合增强 |
| **建议形态** | 独立 **技术升级变更单** |

#### ⑧ 增量更新（只处理新文件）

| | |
|---|---|
| **您感受到** | 库里有 100+ 项目时，**只索引新增/改动的文件**，不用每次 **整库重跑** 等很久 |
| **解决什么** | 日常补几套资料 **更快** |
| **第一期** | 触发索引时偏 **全量**；新文件须管理员 **主动点** 更新 |

#### ⑨ 分角色权限（可选）

| | |
|---|---|
| **您感受到** | 工程师 **只能检索和使用**；管理员 **才能上传、删改、重建索引** |
| **解决什么** | 多人用时 **防误操作** |
| **第一期** | 内网管理员共用；细粒度权限 **不含** |

## 5. 对 IT 的说明

- **R1：** IT 目录批量 **或** 知识库页 **单套/小批量 Web 上传（≤5 套/次）**；开发方提供模板与验收
- **运维：** 备份 / 启停 / 重建索引脚本随 M6 移交
- **扩展：** 新 doc_type 或新应用通过 manifest + ingest 扩展，**不破坏**现有 Engagement 结构
