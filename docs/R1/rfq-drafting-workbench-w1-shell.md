## 1. 客户真实诉求（已对齐）

前期不要「一次生成可解析的正式 RFQ」，而是：

1. 从 PPT/PDF 等沟通材料里**抽出内容**  
2. **拿到变更信息**  
3. 导出一份**大概的草稿 Word**，工程师**离线细化**  
4. 再自行把正式 RFQ **上传到现有 `/rfq` 解析**

系统仍坚持：**正式对标以 Word 为准**；起草台不替代解析，也不让 PPT 直进矩阵。

## 3. 入口（易用性）

在 RFQ 上传区旁并列两扇门（**不**改成强制五步第 0 步）：

| 入口 | 文案建议 | 去向 |
|------|----------|------|
| A | **从沟通材料整理草稿**（PPT/PDF · Demo 预览） | 起草台壳 |
| B | **已有正式 RFQ，开始分析** | 现有上传（主路径不变） |

---

## 4. 壳内五屏（静态走查）

1. **上传** — 选 PPT/PDF；注明本页为预览、不真解析。  
2. **按页看** — 缩略图 + 大图（样例图即可）；可标记「有变更 / 纳入草稿」。  
3. **变更与要点** — 页码 · 抽出文字 · 变更备注（客户最关心的一屏）。  
4. **草稿结构预览** — 示意大纲：项目信息 / 范围与模块 / 变更与差异 / 待补充；注明非贵司正式模板。  
5. **导出** — 「下载草稿 Word（Demo）」→ 成功态；**明确下一步：离线完善后，回本页用入口 B 上传正式 Word**。  
   「送入解析」禁用或不出，避免预期错位。

---

## 5. 与主链路关系

```text
【段 A · 整理】PPT → 起草台壳 → 下载草稿 Word →（离线编辑）
【段 B · 分析】正式 RFQ Word → 现有解析 → 维度 → 矩阵 → 选源
```

段 A 以**下载结束**为闭环；段 B 完全复用现网。
