**版本：** v0.1 · 2026-07-23

**属性：** **R1 合同外 · 变更单 / 二期包候选**  
**关联：** [change-map-vision-spike-plan.md](change-map-vision-spike-plan.md) · 愿景文档「多语言 RFQ / OCR = 首期不含」

## 0. 一句话结论

| 问题 | 结论 |
|------|------|
| 现在能不能做？ | **不能**（仅 Word 文本 RFQ；无 PDF/PPT 解析、无看图、无德语专项、跨语种对标未按德文设计） |
| 两条路线哪个能做？ | **都能做**；差别在 **数据是否出内网、硬件投入、长期成本、可控性** |
| 德语难在哪？ | 不只是「翻译」：图上德文零件名 + 德文 RFQ 正文 + **与中/英历史库比对**，本地还要换/加强 **多语种向量模型** |
| 建议 | 先确认客户 **是否允许 RFQ 图文出内网** → 再选路线；无论哪条都建议 **先 Spike 再报价** |

## 1. 客户需求拆解（相对现状）

### 1.1 需求清单

| # | 客户诉求 | 当前系统 | 缺口 |
|---|----------|----------|------|
| A | RFQ 输入支持 **PDF / PPT**（不仅 Word） | 仅 `.doc`/`.docx` | 文档解析与上传契约 |
| B | 识别 **红旅图**：按绿/红/黄提取文字与图 | 无 | 视觉/OCR + 色标逻辑 |
| C | 图上 **无文字标签** 时：抽出图片，让用户按颜色补全模块需求 | 无 | 图片裁剪归档 + 人工补全 UI |
| D | **德语** PDF/PPT/Word 的 RFQ 需求识别 | Prompt/规则偏中英客户模板 | 德语解析 + 术语 |
| E | 与历史 RFQ **跨语种**（德/中/英）相似比对，作报价参考 | RAG 有，embedding 偏通用英/中实践 | **多语种 embedding** + 入库策略 + 评测 |

> 客户补充：多数德国客户 RFQ 是「带图」形态——红旅图是主路径之一，不是边角需求。

### 1.2 业务能力分层（评估与报价应按层报价）

```text
层 1  容器：能打开 PDF/PPT/Word，抽出「可编辑文字」+「页面/内嵌图」
层 2  红旅图：色标识别 → 有字则结构化；无字则出图给人补
层 3  德语正文：抽出 modules / 交付物 / 里程碑等（对齐现有 RFQ 结构）
层 4  跨语种对标：新 RFQ（德）↔ 历史（中/英/德）相似项目 Top-K → 报价参考
```

层 1–2 偏「看图/抽图」；层 3–4 偏「语言与检索」。两条技术路线主要差在 **层 2（及层 3 的大模型调用方式）**；层 1 与层 4 的工程（抽文档、换 embedding）**两条路线都要做**。

## 2. 路线一：第三方 API（云端大模型看图 + 文本）

### 2.1 技术方案是什么

在现有 ARIA 内网应用上，增加「云端识别适配层」：

1. **本地**完成：PDF/PPT 拆页、抽图、红旅图页筛选、无标签时切图存盘（敏感图是否上传由策略开关控制）。  
2. **调用第三方**（示例量级，非绑定厂商）：带视觉的大模型 API（通义千问 VL、Azure OpenAI GPT-4o、Google Gemini 等）——上传页图或裁切色块图，返回 JSON（零件名、零件号、颜色状态）；德文正文页可走同厂商文本/多模态接口做结构化抽取。  
3. **本地**完成：人工复核 UI、写入任务、与历史库比对（embedding 仍建议本地，见 §4）。  
4. 密钥、审计日志、失败重试、脱敏策略（零件号/客户名打码后再传）放在 `VisionGateway` 一类服务中，**禁止**路由层直连公网。

```text
[工程师上传] → [ARIA 本地拆文档]
            → [可选：打码] → [第三方 Vision/LLM API]
            → [结构化结果回写] → [人工确认] → [本地 RAG 对标]
```

### 2.2 优点 / 风险

| 优点 | 风险与约束 |
|------|------------|
| 看图、德语、复杂版式 **起步快**，准确率通常高于同价位本地小模型 | **RFQ/图纸出内网**——与当前「本地私有化、数据不出域」产品承诺 **直接冲突**，须客户信息安全书面批准 |
| 本地 **不必**为视觉模型加购高端 GPU | 按页/按 token **持续费用**；忙时限流；供应商停服/涨价 |
| 厂商迭代快，少维护模型版本 | 德国汽车客户常有 **严格数据分级**；合同与等保/内审可能直接否决 |
| | 网络依赖；断网即不可用 |
| | Prompt/结果仍须本地 Schema 校验，不能「全信 API」 |

### 2.3 硬件要求（相对现状）

| 组件 | 要求 |
|------|------|
| 应用服务器 | 与现网类似即可（CPU + 内存解析 PDF/PPT） |
| GPU | **视觉可不再依赖本地 VL**；若仍保留本地 `qwen2.5` 做非敏感文本/对标，维持现有 **单卡 24GB（如 4090）** 即可 |
| 磁盘 | 增加页图缓存（高清渲染占空间），建议预留 **≥200GB** 任务临时区（可配置清理） |
| 网络 | **稳定出站 HTTPS** 到厂商；防火墙白名单；建议专线/代理审计 |
| 本地 embedding | 跨语种对标仍建议本地跑多语种向量模型（见 §4）——约 **2–6GB 显存或 CPU**，可与主 LLM 错峰 |

**硬件结论（路线一）：** 主要增量是 **合规与网络**，不是显卡；若客户禁止出网，本路线不可选。

### 2.4 德语支持（路线一）

| 点 | 说明 |
|----|------|
| 图上德文标签 | 主流云端 VL 对拉丁字母/德文零件名一般可用；密图仍要样本评测 |
| 德文 RFQ 正文 | 云端文本/多模态模型德语能力通常强于本地 14B |
| 与中/英历史比对 | **不建议**把全库历史文档都送云端；应用本地 **多语种 embedding** 做相似检索，仅把「当前 RFQ 摘要」可选送云做结构化 |
| 术语 | 仍需客户提供德文零件/模块词表或样例，减少「译错模块名」 |

## 3. 路线二：本地大模型看图 + 文本（Ollama 等）

### 3.1 技术方案是什么

保持 **数据不出内网**，在现有 Ollama 体系上扩展：

1. **文档层（本地库）：** PDF（如 PyMuPDF）、PPT（python-pptx + 页渲染）→ 文字层 + 图片/整页图。  
2. **红旅图层：**  
   - 有标签：本地 **视觉模型（VL）** 和/或 **色块检测 + 德文 OCR** → JSON；  
   - 无标签：按颜色区域裁图 → 任务附件，UI 让工程师补模块信息。  
3. **德语 RFQ 正文：** 本地文本模型（建议升级为多语种更强的 Qwen2.5 32B 或同级）做结构化抽取。  
4. **跨语种对标：** 更换/增加 **多语种 Embedding**（如 bge-m3 一类），历史库 **按新模型重建索引**；检索德文 query 命中中/英历史 chunk。  
5. 人工复核强制；与现有 `task_jobs` / Ollama 租约集成（视觉任务更长、更吃显存）。

```text
[上传] → [本地拆 PDF/PPT/Word]
      → [本地 VL / OCR] → [本地文本 LLM 结构化]
      → [人工确认]
      → [本地多语种向量检索] → [对标矩阵 / 报价参考]
```

### 3.2 优点 / 风险

| 优点 | 风险与约束 |
|------|------------|
| **符合**当前产品与客户「数据不出内网」叙事 | 密标签红旅图准确率可能低于顶级云端 VL，**必须 Spike** |
| 无按次 API 费；断网可用 | **显存与排队压力大**：VL + 32B 文本 + embedding 难同驻一张 24GB 卡 |
| 全链路可审计、可版本钉死 | 模型下载、驱动、运维由客户 IT + 我方共同承担 |
| | 德语质量依赖模型选型与 Prompt；需德文样本回归集 |

### 3.3 硬件要求（重点）

以下为 **经验量级**（量化部署），正式以 Spike 实测为准。

#### 方案 2a · 单卡 24GB（现网常见 4090）——「能跑，但会排队」

| 模型角色 | 建议 | 显存粗估 |
|----------|------|----------|
| 文本 LLM | `qwen2.5:32b` Q4 **或** 继续 14B（德语弱一些） | ~18–22GB / ~10–16GB |
| 视觉 VL | `qwen2.5-vl:7b`（或同级 7–8B VL） | ~8–12GB |
| Embedding | 多语种模型（如 bge-m3） | ~2–4GB |

**现实约束：** 24GB **无法**同时常驻「32B 文本 + VL」。只能：

- **串行换模**（慢、伤 SSD/启动时间），或  
- 文本用 14B + VL 7B 错峰加载，或  
- 红旅图走「色块 + OCR」、尽量不加载 VL（准确率另测）

与现网 `OLLAMA_MAX_CONCURRENT=1` 叠加后：多人上传德文 PDF/红旅图时，等待会 **明显长于** 现在的 Word RFQ。

#### 方案 2b · 推荐生产形态 · 双卡或 48GB+

| 配置 | 用途 |
|------|------|
| **GPU1（24GB+）** | 文本 `qwen2.5:32b`（德语结构化 + 对标说明） |
| **GPU2（16–24GB）** | 视觉 VL 7B/14B + 多语种 embedding |
| 或单卡 **48GB**（如 A6000） | 文本 + VL 同机分区，运维简单一些 |

| 其他 | 要求 |
|------|------|
| 系统内存 | ≥64GB（PDF 渲染 + worker） |
| 数据盘 | 页图缓存 + 模型文件：**建议 ≥1TB**（多模型体积大） |
| CPU | 16 核+ 利于 PDF 渲染与 OCR |

**硬件结论（路线二）：**  
- **仅维持一张 4090：** 可做 Spike / 小流量试点，**不适合**「多数德国 RFQ 都是带图」的日常高峰。  
- **要达到客户描述的主路径：** 预算上应按 **第二块 GPU 或更大显存** 评估。

### 3.4 德语支持（路线二）

| 点 | 说明 |
|----|------|
| 正文理解 | Qwen2.5 系列具备多语能力；**生产建议 32B**；须用真实德文 RFQ 建回归集（modules/里程碑） |
| 图上 OCR | 须显式启用 **德文/拉丁** OCR 语言包；零件号（如 `8BD.881.xxx`）规则校验可补洞 |
| 跨语种检索 | 现网 `nomic-embed-text` **不足以**作为德↔中/英主方案 → 换 **多语种 embedding** 并 **全库 reindex** |
| 历史库语言 | 入库时记录 `lang`；评测集须含「德文 query → 中文/英文历史命中」用例 |
| 人工 | 德文术语仍建议工程师确认，尤其是模块归类进报价 Function |

## 4. 两条路线都要做的「非模型」工程（易漏估）

| 项 | 说明 | 粗估量级（正式开发，不含 Spike） |
|----|------|----------------------------------|
| PDF/PPT 解析与上传 | 格式校验、页渲染、内嵌图、病毒/体积限制 | 中 |
| 红旅图无标签路径 | 按色切图 + 补全表单 UI | 中 |
| 德语 Prompt / 规则 | 与现有中英 RFQ 结构对齐 | 中 |
| 多语种 embedding + reindex | 历史库重建、检索评测 ≥15 条跨语种 | 中高 |
| 人工复核与权限 | 图文对照编辑 | 中 |
| 安全与审计 | 路线一：出网审批；路线二：模型供应链 | 视客户 |

**跨语种对标**不等于「把德文翻译成中文再搜」一种做法；更稳的是 **同一向量空间多语检索**（多语种 embedding）。翻译可作辅助，不宜作唯一路径。

## 5. 对照总表（给决策用）

| 维度 | 路线一 · 第三方 API | 路线二 · 本地模型 |
|------|---------------------|-------------------|
| 数据出境 | **通常要出网** | **不出网** |
| 与现产品承诺 | 冲突，需改承诺/特批 | 一致 |
| 看图/德语起步质量 | 往往更好、更快 | 依赖选型与显存；需 Spike |
| 本地 GPU | 低（可维持现卡） | **高**（建议双卡或 48GB+） |
| 持续费用 | API 按量 | 电费 + 硬件折旧 |
| 运维 | 密钥、限流、厂商变更 | 模型、显存、排队 |
| 断网 | 不可用 | 可用 |
| 适合谁 | 允许云、要快上、图复杂 | 主机厂/强保密、已投本地算力 |

## 6. 德语专项风险（两条路线共用）

1. **红旅图**：德文名 + 小号字 + 照片翻拍摩尔纹 → 漏检、错号；无标签页只能 **人机共补**。  
2. **RFQ 结构**：德国客户模板与现有中文 Word RFQ 规则 **不能直接复用**，要单独样本。  
3. **跨语种相似**：字面不同但工程含义相近（如 Sitz / 座椅 / Seat）靠 embedding 与领域词表，**必须评测**，不能口头承诺「和中文一样准」。  
4. **报价参考**：相似历史命中后，人天仍走现有确认流；德文结果 **禁止**无复核直出报价。

## 7. 建议推进方式（对内）

1. **先问客户 PM 两个是非题**（非技术）：  
   - 红旅图/RFQ **能不能离开公司内网**？  
   - 带图德文 RFQ 是「锦上添花」还是「德国客户主路径」（影响是否上第二块 GPU）。  
2. 出网 **禁止** → 只推路线二 + 硬件增配评估。  
3. 出网 **允许且信息安全签字** → 可用路线一做红旅图/德语抽取加速，**检索与历史库仍建议本地**。  
4. 无论哪条：扩大现有 Spike（见 change-map 计划）覆盖 **德语正文 + 跨语种检索**，再出变更单人日与报价。  
5. **不阻塞 R1 签字**；本包单独立项。

### Spike 增量（相对原红旅图 Spike）

| 新增 | 目的 |
|------|------|
| 德文 Word/PDF/PPT 正文结构化准确率 | 层 3 |
| 多语种 embedding A/B（现 nomic vs 多语种） | 层 4 |
| 路线一（若客户允许）小流量 API 对照准确率/时延/费用 | 决策依据 |
| 无标签红旅图切图 + 人工补全原型 | 需求 C |

## 8. 给客户 PM 的口述版（可选）

- 现在系统像「只读 Word 说明书」；德国常见的是「带彩图的 PDF/PPT 说明书」，还要认颜色、认德文。  
- **两条路：**  
  - **上网找外部 AI 帮忙看图**——上线快、公司电脑不用大升级，但图纸可能要传到外部，要贵司信息安全点头，并按用量付费。  
  - **全部在公司自己电脑里认**——数据更安心，但要加配显卡或更强服务器，开发验证时间更长。  
- 和历史项目比对时，还要让系统在「德文新项目」和「中文/英文老项目」之间找到相似项，这需要单独调试，不是打开翻译软件就结束。  
- 建议：先定能不能出网 → 再拿几份真实德文带图 RFQ 做小范围试认 → 再谈费用与上线时间。当前第一期按原范围继续即可。
